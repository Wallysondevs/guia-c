C Sanitizers (-fsanitize)

Em C, muitos erros de memória não derrubam o programa: ler uma posição depois do fim do array, usar memória já devolvida com free, somar além do maior int. O programa segue, mostra um número estranho (ou até o número certo, por sorte) e o erro fica escondido até o dia em que causa um estrago. Os sanitizers são fiscais que o compilador coloca dentro do seu programa: com uma opção a mais no gcc, cada acesso à memória e cada conta passam a ser conferidos, e o primeiro erro vira um relatório com o arquivo e a linha.

Você vai aprender
  • O que é um sanitizer e por que ele acha erros que o compilador e o teste "rodou e deu certo" não acham.
  • A ligar o AddressSanitizer (-fsanitize=address) e ler o relatório de: estouro de array na pilha e no heap, uso depois do free, free duplo e vazamento de memória.
  • A ligar o UndefinedBehaviorSanitizer (-fsanitize=undefined) e ler os runtime error de estouro de int e de deslocamento de bits.
  • Por que compilar com -g junto, quanto o sanitizer custa e quando usar.
  • O que funciona (e o que não funciona) no editor do guia.

Todos os relatórios desta aula são reais, feitos com o gcc 15 na máquina fictícia da Ana, na pasta ~/c/san. Os sanitizers fazem parte do gcc e do Clang no Linux; não precisa instalar nada. No editor do guia eles não funcionam (o motivo e o que dá para fazer lá estão na seção 9): as caixas "Experimente" servem para consertar os erros que os relatórios encontraram.

A ideia: o fiscal dentro do programa

Pense numa lojinha sem câmeras: se alguém pega um produto da prateleira do vizinho, ninguém vê, e a falta só aparece no fim do mês, sem pista de quem foi. Agora coloque um fiscal ao lado de cada prateleira, anotando tudo: no primeiro produto pego do lugar errado, ele apita, diz qual prateleira, quem pegou e quando aquele produto chegou. A loja fica mais lenta (o fiscal confere tudo), mas o erro é pego na hora.

O sanitizer é esse fiscal. Com -fsanitize=…, o compilador acrescenta uma conferência antes de cada leitura e escrita na memória (ou antes de cada conta), e o programa passa a ser ligado a uma biblioteca que guarda um mapa de qual memória pode ser usada. O nome vem do inglês sanitize, "higienizar": o programa sai "limpo" de erros que antes passavam calados.

SanitizerOpçãoAcha
AddressSanitizer (ASan, "fiscal de endereços")-fsanitize=addressEstouro de array (pilha e heap), uso depois do free, free duplo, vazamentos (com o LeakSanitizer embutido).
UndefinedBehaviorSanitizer (UBSan, "fiscal de comportamento indefinido")-fsanitize=undefinedEstouro de int com sinal, deslocamento de bits grande demais, divisão por zero, índice fora do array declarado, ponteiro nulo e outros comportamentos indefinidos.

1. Um erro que passa calado

A Ana quer somar as 5 notas de um aluno. Repare no <= do for:

#include <stdio.h>

int main(void) {
    int notas[5] = {7, 8, 10, 6, 9};
    int soma = 0;
    for (int i = 0; i <= 5; i++) {
        soma += notas[i];
    }
    printf("Soma: %d\n", soma);
    return 0;
}

$ gcc -std=c23 -Wall -Wextra -g notas.c -o notas
$ ./notas
Soma: 40

Nenhum aviso, nenhum crash, e a soma está até certa (7 + 8 + 10 + 6 + 9 = 40). Mas o laço roda com i de 0 a 5, e notas[5] não existe: o array vai de notas[0] a notas[4] (veja Arrays). O programa leu a memória que vem logo depois do array, que por acaso valia 0. Em outro computador, com outro compilador ou depois de uma mudança qualquer no código, ali pode estar outro número, e a soma sai errada.

Assusta, mas só umas poucas linhas importam. Vamos ler de cima para baixo:

==35068==ERROR: AddressSanitizer: stack-buffer-overflow
O tipo do erro. 35068 é o número do processo (o PID), que muda a cada execução. stack-buffer-overflow = "estouro de um buffer na pilha": um array local (as variáveis locais moram na pilha) foi acessado fora dos limites. Os números 0x… da linha são endereços; não precisa deles.
READ of size 4
"Leitura de 4 bytes": o programa tentou ler um int (4 bytes). Se fosse WRITE, seria uma escrita, que é ainda mais perigosa.
#0 … in main /home/ana/c/san/notas.c:7
A pilha de chamadas do erro, como o backtrace do gdb. O #0 é onde aconteceu: função main, arquivo notas.c, linha 7 (soma += notas[i];). As linhas #1 a #3 são da biblioteca do C, que chamou o main: pode ignorar.
This frame has 1 object(s): [32, 52) 'notas' (line 4)
O ASan diz qual variável foi estourada: o array notas, declarado na linha 4, ocupa os bytes 32 a 51 (são 20 bytes: 5 int de 4 bytes). O [32, 52) quer dizer "do 32 até antes do 52".
<== Memory access at offset 52 overflows this variable
"O acesso no byte 52 passa do fim desta variável": exatamente o primeiro byte depois de notas[4], ou seja, notas[5].
HINT: this may be a false positive…
Uma dica genérica ("pode ser alarme falso se o seu programa usa truques especiais com a pilha"). Não é o seu caso; pode ignorar.
SUMMARY: … notas.c:7 in main
O resumo em uma linha: tipo do erro, arquivo, linha e função. Se for ler só uma linha, leia esta.
Shadow bytes around the buggy address
O "mapa da sombra": como o ASan marca cada pedaço da memória (00 = pode usar, f1/f3 = zonas proibidas em volta do array). É útil para quem desenvolve o ASan; você pode pular.
==35068==ABORTING e o código 1
O ASan encerra o programa no primeiro erro, com código de saída 1. O printf("Soma: …") nem chegou a rodar.

Receita de leitura: procure a linha ERROR: (o tipo), a primeira linha #0 que aponta para um arquivo seu (o lugar) e o SUMMARY. O resto é detalhe.

3. Estouro no heap: o + 1 esquecido

O erro mais clássico de string em C: reservar espaço para as letras e esquecer o '\0' do fim (veja Strings Dinâmicas):

#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void) {
    const char *texto = "Ana Maria";
    char *copia = malloc(strlen(texto));
    if (copia == NULL) {
        return 1;
    }
    strcpy(copia, texto);
    printf("%s\n", copia);
    free(copia);
    return 0;
}

4. Usar a memória depois do free

Depois do free, a memória volta para o sistema e pode ser entregue a outro malloc. O ponteiro, porém, continua guardando o endereço antigo (veja malloc e free):

#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int *pontos = malloc(3 * sizeof *pontos);
    if (pontos == NULL) {
        return 1;
    }
    pontos[0] = 10;
    free(pontos);
    printf("Pontos: %d\n", pontos[0]);
    return 0;
}

$ gcc -std=c23 -Wall -Wextra -g depois.c -o depois
depois.c: In function ‘main’:
depois.c:11:5: warning: pointer ‘pontos’ used after ‘free’ [-Wuse-after-free]
   11 |     printf("Pontos: %d\n", pontos[0]);
      |     ^~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
depois.c:10:5: note: call to ‘free’ here
   10 |     free(pontos);
      |     ^~~~~~~~~~~~
$ ./depois
Pontos: -1245621546

Aqui o gcc 15 até avisou ("ponteiro pontos usado depois do free"), porque o free e o uso estão juntos, na mesma função. Em programas de verdade, o free costuma estar longe, em outra função ou outro arquivo, e o compilador não vê. O sanitizer vê sempre, porque confere enquanto o programa roda:

5. free duas vezes

#include <stdlib.h>
#include <string.h>

int main(void) {
    char *nome = malloc(20);
    if (nome == NULL) {
        return 1;
    }
    strcpy(nome, "Ana");
    free(nome);
    free(nome);
    return 0;
}

6. Vazamentos: o LeakSanitizer

Um vazamento é memória reservada com malloc que nunca é devolvida com free (veja Vazamentos de Memória). O ASan traz junto um terceiro fiscal, o LeakSanitizer ("fiscal de vazamentos"), que confere tudo quando o programa termina:

#include <stdio.h>
#include <stdlib.h>
#include <string.h>

char *copiar(const char *texto) {
    char *copia = malloc(strlen(texto) + 1);
    if (copia != NULL) {
        strcpy(copia, texto);
    }
    return copia;
}

int main(void) {
    char *item = copiar("arroz");
    printf("Item: %s\n", item);
    return 0;
}

O programa rodou inteiro. O relatório só aparece no fim, quando o LeakSanitizer confere o que não foi devolvido.

"Vazamento direto de 6 bytes em 1 bloco": "arroz" tem 5 letras + o '\0'. Direto quer dizer que nenhum ponteiro aponta mais para o bloco.

código de saída 1
Mesmo com o programa tendo funcionado, o código de saída vira 1: um vazamento conta como erro.

7. UndefinedBehaviorSanitizer: -fsanitize=undefined

O segundo fiscal confere as contas e outras operações que o C deixa sem regra (o comportamento indefinido). Dois exemplos clássicos: passar do maior int (veja Inteiros) e deslocar bits demais (veja Operadores de Bits):

#include <stdio.h>
#include <limits.h>

int main(void) {
    int visitas = INT_MAX;
    visitas = visitas + 1;
    printf("Visitas: %d\n", visitas);

    int bits = 40;
    unsigned int mascara = 1u << bits;
    printf("Máscara: %u\n", mascara);
    return 0;
}

$ gcc -std=c23 -Wall -Wextra -g conta.c -o conta
$ ./conta
Visitas: -2147483648
Máscara: 256
$ gcc -std=c23 -Wall -Wextra -g -fsanitize=undefined conta.c -o conta
$ ./conta
conta.c:6:13: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
Visitas: -2147483648
conta.c:10:31: runtime error: shift exponent 40 is too large for 32-bit type 'unsigned int'
Máscara: 256
$ echo $?
0
conta.c:6:13:
Arquivo, linha e coluna, no mesmo formato das mensagens do compilador. A coluna 13 é o + de visitas + 1.
runtime error:
"Erro em tempo de execução": foi achado enquanto o programa rodava, não na compilação.
signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
"Estouro de inteiro com sinal: 2147483647 + 1 não cabe no tipo int". O resultado, -2147483648, foi a máquina "dando a volta", mas o C não promete isso: com otimização, o compilador pode fazer qualquer coisa.
shift exponent 40 is too large for 32-bit type 'unsigned int'
"O deslocamento de 40 é grande demais para um tipo de 32 bits". Deslocar um unsigned int por 32 ou mais é indefinido. O 256 que saiu é o que o processador da Ana faz (ele usa só os 5 bits de baixo de 40, que dão 8, e 1 << 8 = 256); outro processador pode dar 0.
echo $? → 0
Diferente do ASan, o UBSan avisa e deixa o programa seguir: por isso os dois printf rodaram e o código de saída é 0.

Para o programa parar no primeiro erro do UBSan (útil em testes automáticos, que olham o código de saída), acrescente -fno-sanitize-recover=undefined ("não se recupere"):

$ gcc -std=c23 -Wall -Wextra -g -fsanitize=undefined -fno-sanitize-recover=undefined conta.c -o conta
$ ./conta
conta.c:6:13: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
$ echo $?
1

8. Os dois juntos, e o papel do -g

O ASan e o UBSan combinam bem. Separe os nomes por vírgula:

9. O custo, e o editor do guia

O fiscal confere tudo, e isso custa. Um programa que soma um milhão de números 200 vezes, com e sem sanitizers:

#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int n = 1000000;
    int *v = malloc(n * sizeof *v);
    if (v == NULL) {
        return 1;
    }
    long long soma = 0;
    for (int volta = 0; volta < 200; volta++) {
        for (int i = 0; i < n; i++) {
            v[i] = i % 7;
            soma += v[i];
        }
    }
    printf("Soma: %lld\n", soma);
    free(v);
    return 0;
}

$ gcc -std=c23 -Wall -Wextra -g pesado.c -o pesado
$ gcc -std=c23 -Wall -Wextra -g -fsanitize=address,undefined pesado.c -o pesado-san
$ time ./pesado
Soma: 599999400

real	0m1,081s
user	0m1,077s
sys	0m0,004s
$ time ./pesado-san
Soma: 599999400

real	0m2,558s
user	0m2,549s
sys	0m0,009s
$ ls -l pesado pesado-san
-rwxrwxr-x 1 ana ana 17632 out 17 10:35 pesado
-rwxrwxr-x 1 ana ana 28472 out 17 10:35 pesado-san

Mais de duas vezes mais lento e com um executável maior (e, enquanto roda, o ASan usa bem mais memória, para o mapa da sombra). Em geral, o ASan deixa o programa umas 2 vezes mais lento; o UBSan, menos. É um preço ótimo enquanto você desenvolve e testa, e um preço ruim para o programa que vai para os usuários. Por isso a regra é: sanitizers no desenvolvimento e nos testes; a versão final sem eles (veja CMake e Makefile para ter as duas versões).

No editor do guia

O editor roda o seu programa em WebAssembly, e as bibliotecas dos sanitizers não existem lá. Pedir -fsanitize=address num data-flags dá erro na hora de ligar:

wasm-ld: error: /tmp/notas-62bf3f.o: undefined symbol: __asan_option_detect_stack_use_after_return
wasm-ld: error: /tmp/notas-62bf3f.o: undefined symbol: __asan_stack_malloc_1
«… mais linhas iguais …»
clang: error: linker command failed with exit code 1 (use -v to see invocation)

Mas há um modo do UBSan que funciona no editor: o modo armadilha, -fsanitize=undefined -fsanitize-trap=undefined. Nele não existe relatório: o fiscal só para o programa no primeiro erro. No editor, a parada aparece como Falha de segmentação (139). No Linux, como Instrução ilegal:

$ gcc -std=c23 -Wall -Wextra -g -fsanitize=undefined -fsanitize-trap=undefined conta.c -o conta-trap
$ ./conta-trap
Instrução ilegal         (imagem do núcleo gravada) ./conta-trap
$ echo $?
132

Missão: esta caixa compila com o UBSan em modo armadilha. Rode e veja o programa parar logo no primeiro erro. Depois conserte os dois erros que o relatório da seção 7 apontou: use long long para visitas (com %lld no printf) e unsigned long long para mascara, com 1ull << bits e %llu (veja Inteiros). A saída deve ser Visitas: 2147483648 e Máscara: 1099511627776.

#include <stdio.h>
#include <limits.h>

int main(void) {
    int visitas = INT_MAX;
    visitas = visitas + 1;
    printf("Visitas: %d\n", visitas);

    int bits = 40;
    unsigned int mascara = 1u << bits;
    printf("Máscara: %u\n", mascara);
    return 0;
}

#include <stdio.h>
#include <limits.h>

int main(void) {
    long long visitas = INT_MAX;
    visitas = visitas + 1;
    printf("Visitas: %lld\n", visitas);

    int bits = 40;
    unsigned long long mascara = 1ull << bits;
    printf("Máscara: %llu\n", mascara);
    return 0;
}

Qual usar: durante o desenvolvimento, compile com -g -fsanitize=address,undefined e rode os seus testes. O Clang tem ainda outros fiscais: -fsanitize=memory (variáveis sem valor inicial, só no Clang) e -fsanitize=thread (erros entre threads; não combina com o address).

Como resolver: passe o mesmo -fsanitize=… em todas as etapas: na compilação de cada .c e na ligação.

O que aconteceu: erro de digitação no nome do sanitizer ("argumento não reconhecido; você quis dizer address?").

Como resolver: address tem dois d e dois s.

cc1: error: ‘-fsanitize=thread’ is incompatible with ‘-fsanitize=address’

O que aconteceu: o ASan e o TSan usam a memória de jeitos que não combinam ("é incompatível").

Como resolver: compile duas versões e teste uma de cada vez.

O que aconteceu: os dois fiscais querem controlar a memória ao mesmo tempo. O programa nem rodou de verdade.

O que aconteceu: faltou o -g.

Resumo

  • Muitos erros de memória em C não derrubam o programa: o resultado pode até parecer certo. Os sanitizers colocam um fiscal dentro do programa, que para (ou avisa) no primeiro erro.
  • -fsanitize=address (ASan): estouro de array na pilha e no heap, uso depois do free, free duplo e, no fim, vazamentos. Ele aborta no primeiro erro, com código 1.
  • -fsanitize=undefined (UBSan): estouro de int, deslocamento grande demais, divisão por zero… Ele avisa com runtime error e segue (a não ser com -fno-sanitize-recover=undefined).
  • Para ler o relatório: o tipo na linha ERROR, a primeira linha #N com um arquivo seu e o SUMMARY. Compile sempre com -g.
  • Custa velocidade e memória: use no desenvolvimento e nos testes, não na versão final. Passe a opção em todas as etapas (compilação e ligação).
  • No editor do guia, só o modo armadilha do UBSan funciona; o resto, no seu Linux.
