C Depurar com gdb

O programa morreu com "Falha de segmentação" e não disse onde. Ou a média deu 8,00 quando deveria dar 8,33. Você pode encher o código de printf para descobrir o que está acontecendo, ou pode usar um depurador: um programa que roda o seu programa em câmera lenta, deixa você parar em qualquer linha e olhar o valor de cada variável. No Linux, o depurador clássico é o gdb (GNU Debugger, "depurador do GNU"). Nesta aula você vai usá-lo para achar a linha exata de um crash e para caçar um erro de conta, passo a passo.

Você vai aprender
  • Como preparar o programa para depuração: a opção -g do gcc (e por que sem -O2).
  • Como rodar dentro do gdb (gdb ./programa, run) e achar a linha de um crash com backtrace.
  • Como olhar variáveis com print, trocar de função com frame e acompanhar valores com display.
  • Como pausar o programa numa linha (break) e andar linha a linha (next e step).
  • Como seguir em frente (continue, finish) e sair (quit).
  • O atalho gdb -batch -ex run -ex bt ./programa, que transforma "Falha de segmentação" em "linha 19".

Todas as sessões desta aula são reais, feitas com o gdb 17.1 e o gcc 15 na máquina fictícia da Ana, na pasta ~/c/gdb. O gdb não funciona no editor do guia: ele precisa controlar um programa de verdade no seu sistema. Para praticar, instale-o (no Ubuntu e no Debian: sudo apt install gdb; veja Instalar no Linux). As caixas "Experimente" desta página servem para corrigir, no editor, os erros que o gdb encontrou.

1. Preparar o programa: -g

O executável que o gcc gera normalmente não guarda os nomes das variáveis nem os números das linhas: o processador não precisa disso para rodar. Para o depurador poder dizer "linha 19, variável a", compile com a opção -g, que acrescenta essas informações de depuração ao executável:

$ gcc -std=c23 -Wall -Wextra -g crash.c -o crash
gcc -std=c23 -Wall -Wextra
O comando padrão do guia (veja Compilar com gcc).
-g
"Guarde as informações de depuração": nomes de variáveis, de funções e a ligação entre cada pedaço do programa e a linha do .c de onde ele veio. O programa fica maior, mas roda igual.
crash.c -o crash
O arquivo de entrada e o nome do executável, como sempre.

E deixe as otimizações desligadas, que é o padrão do gcc (chamado -O0, "nível zero de otimização"). Com -O2, o compilador reorganiza, junta e apaga linhas, e o passo a passo fica confuso (seção 6). Resumo: para depurar, -g e sem -O2.

2. Achar a linha de um crash

Este programa procura alunos numa turma. A função buscar devolve um ponteiro para o aluno encontrado, ou NULL se não achar (veja Ponteiro Nulo e Structs e Ponteiros):

#include <stdio.h>
#include <string.h>

struct aluno {
    char nome[20];
    double nota;
};

struct aluno *buscar(struct aluno turma[], int n, const char *nome) {
    for (int i = 0; i < n; i++) {
        if (strcmp(turma[i].nome, nome) == 0) {
            return &turma[i];
        }
    }
    return NULL;
}

void mostrar(const struct aluno *a) {
    printf("%s: %.1f\n", a->nome, a->nota);
}

int main(void) {
    struct aluno turma[] = {{"Ana", 9.5}, {"Bruno", 7.0}};
    mostrar(buscar(turma, 2, "Ana"));
    mostrar(buscar(turma, 2, "Zeca"));
    printf("Fim.\n");
    return 0;
}

$ gcc -std=c23 -Wall -Wextra -g crash.c -o crash
$ ./crash
Ana: 9.5
Falha de segmentação     (imagem do núcleo gravada) ./crash
$ echo $?
139

"Como chegamos aqui?": backtrace

(gdb) backtrace
#0  0x000055555555522e in mostrar (a=0x0) at crash.c:19
#1  0x0000555555555313 in main () at crash.c:25

O backtrace ("rastro para trás", atalho bt) mostra a pilha de chamadas: quem chamou quem até chegar ao erro (veja Pilha e Heap). Leia de baixo para cima:

  • #1 main () at crash.c:25: o main, na linha 25, chamou…
  • #0 mostrar (a=0x0) at crash.c:19: …a função mostrar, que quebrou na linha 19.

Cada linha da pilha se chama quadro (em inglês, frame), numerado a partir de 0. O #0 é sempre onde o programa está agora.

Quit anyway? (y or n) y

O quit (atalho q) sai do gdb. Como o programa ainda estava congelado, o gdb avisa que vai encerrá-lo ("Inferior 1" é como o gdb chama o programa que ele controla) e pergunta se pode: y (yes, sim).

3. Atalho: tudo numa linha com -batch

Quando você só quer saber onde o programa quebrou, dá para passar os comandos direto na linha de comando. -batch ("em lote") roda os comandos e sai sozinho; cada -ex (execute) é um comando:

$ gdb -batch -ex run -ex bt ./crash
[Thread debugging using libthread_db enabled]
Using host libthread_db library "/usr/lib/x86_64-linux-gnu/libthread_db.so.1".
Ana: 9.5

Program received signal SIGSEGV, Segmentation fault.
0x000055555555522e in mostrar (a=0x0) at crash.c:19
19	    printf("%s: %.1f\n", a->nome, a->nota);
#0  0x000055555555522e in mostrar (a=0x0) at crash.c:19
#1  0x0000555555555313 in main () at crash.c:25

Guarde este comando: gdb -batch -ex run -ex bt ./programa é a forma mais rápida de transformar "Falha de segmentação" em "linha 19".

Quando o quadro #0 é da biblioteca

Muitas vezes o programa quebra dentro de uma função da biblioteca do C, como strlen, strcpy ou printf. Este programa conta as letras de cada palavra de uma lista, mas o último item é NULL:

#include <stdio.h>
#include <string.h>

size_t letras(const char *palavra) {
    return strlen(palavra);
}

int main(void) {
    const char *lista[] = {"arroz", "feijão", NULL};
    for (int i = 0; i < 3; i++) {
        printf("%zu\n", letras(lista[i]));
    }
    return 0;
}

$ gcc -std=c23 -Wall -Wextra -g conta.c -o conta
$ ./conta

7

$ gdb -batch -ex run -ex bt ./conta
[Thread debugging using libthread_db enabled]

O programa congelou dentro da versão do strlen que a biblioteca do C (a glibc) escolheu para o processador da Ana. No seu computador, o nome pode ser outro (__strlen_evex, __strlen_sse2…).

O gdb queria mostrar o código-fonte do strlen, mas ele não está instalado. Normal; pode ignorar.
#1 letras (palavra=0x0) at conta.c:5
A primeira linha que é de um arquivo seu: aqui está a pista. A função letras passou palavra=0x0 (nulo) para o strlen.
#2 main () at conta.c:11
E quem chamou letras foi o main, na linha 11, dentro do laço.

Regra prática: o erro quase nunca é da biblioteca. Ela só recebeu algo estragado do seu código. Desça o backtrace até a primeira linha com um arquivo seu. (Repare também no 7: "feijão" tem 6 letras, mas 7 bytes, porque o ã ocupa 2 bytes em UTF-8. Veja Acentos e UTF-8.)

4. Andar linha a linha: break, next, step

Nem todo erro derruba o programa. Este calcula a média de 7, 8 e 10, que é 8,33…, mas mostra 8,00:

#include <stdio.h>

double media(const int notas[], int n) {
    int soma = 0;
    for (int i = 0; i < n; i++) {
        soma += notas[i];
    }
    return soma / n;
}

int main(void) {
    int notas[] = {7, 8, 10};
    double m = media(notas, 3);
    printf("Média: %.2f\n", m);
    return 0;
}

$ gcc -std=c23 -Wall -Wextra -g media.c -o media
$ ./media
Média: 8.00

Nenhum aviso, nenhum crash, só um resultado errado. Vamos assistir em câmera lenta. Antes, um erro comum: mandar andar uma linha sem o programa estar rodando.

$ gdb -q ./media

5. next ou step?

O step entra em qualquer função que tenha informações de depuração. Nas funções da biblioteca do C (printf, strlen…), normalmente ele passa direto, porque o Ubuntu não instala o código delas. Mas se você der step ou next na última linha do main, cai no código que chamou o main:

(gdb) next
16	}
(gdb) next
__libc_start_call_main (main=main@entry=0x5555555551be <main>,
    argc=argc@entry=1, argv=argv@entry=0x7fffffffec18)
    at ../sysdeps/nptl/libc_start_call_main.h:83
⚠️ aviso: 83	../sysdeps/nptl/libc_start_call_main.h: Arquivo ou diretório inexistente
(gdb) next
[Inferior 1 (process 28051) exited normally]

__libc_start_call_main é a função da glibc que chama o seu main e, quando ele volta, encerra o programa com o código devolvido (veja Encerrar o Programa). Não há nada para ver ali: dê continue. Regra prática: next por padrão; step só nas linhas que chamam funções suas; e, se entrou onde não queria, finish volta para quem chamou.

6. Por que depurar sem -O2

Com otimização, o compilador reescreve o programa à vontade. O mesmo media.c, compilado com -O2 -g:

$ gcc -std=c23 -Wall -Wextra -O2 -g media.c -o media-O2
$ gdb -q ./media-O2
Reading symbols from ./media-O2...
(gdb) break media

O ponto de parada em media existe (o info breakpoints, "informações dos pontos de parada", lista ele), mas o programa rodou até o fim sem parar. Com -O2, o gcc copiou o código de media para dentro do main (isso se chama inlining; veja Funções inline), e a função original nunca é chamada. Com otimização também é comum o gdb mostrar <optimized out> ("removida pela otimização") no lugar de uma variável, e o next pular de um lado para o outro. Para depurar, compile com -g e sem -O2 (ou com -Og, uma otimização leve feita para não atrapalhar a depuração).

As IDEs têm depuradores visuais (veja Editores e IDEs): você clica na margem para marcar um ponto de parada, usa botões para Step Over (o next), Step Into (o step), Step Out (o finish) e Continue, e vê as variáveis numa janela, sem digitar print. Qual usar: para "onde quebrou?", o atalho -batch; para "por que o resultado está errado?", o gdb interativo ou o da sua IDE.

Quando dá errado

"No symbol "x" in current context."

O que aconteceu: a variável não existe no quadro atual: ela é de outra função, ou de um bloco que já terminou, ou o programa nem está rodando.

Como resolver: veja os quadros com backtrace e mude com frame N. Se o programa não estiver rodando, marque um break e dê run.

"The program is not being run."

O que aconteceu: você deu next, step ou continue antes do run, ou depois de o programa terminar (exited normally).

Como resolver: marque um ponto de parada (break main) e dê run.

O backtrace mostra só mostrar (), sem arquivo nem linha

O que aconteceu: o programa foi compilado sem -g.

Como resolver: compile de novo com -g e repita.

O programa passou pelo ponto de parada sem parar; <optimized out>; o next pula linhas

O que aconteceu: o programa foi compilado com otimização (-O2, -O3).

Como resolver: compile com -g e sem -O2 (ou com -Og).

O quadro #0 é um nome estranho, como __strlen_avx2_rtm

O que aconteceu: o programa quebrou dentro da biblioteca do C, que recebeu um argumento ruim (um ponteiro nulo, uma string sem '\0').

Como resolver: desça o backtrace até o primeiro quadro com at seu-arquivo.c:N, vá até ele com frame N e olhe os argumentos com print.

"gdb: comando não encontrado"

O que aconteceu: o gdb não está instalado.

Como resolver: no Ubuntu e no Debian, sudo apt install gdb. No macOS, use o lldb, que vem com as ferramentas do Xcode.

Resumo

  • Compile com -g e sem -O2 para depurar.
  • gdb -q ./prog abre; run roda; num crash, o gdb congela o programa no ponto do erro e mostra arquivo, linha e parâmetros.
  • backtrace mostra quem chamou quem; a primeira linha com um arquivo seu é a pista. frame N muda de quadro; print mostra variáveis e expressões; display mostra a cada passo.
  • break pausa numa função ou linha; next anda sem entrar em funções; step entra; continue segue; finish sai da função atual; quit sai.
  • Atalho para crashes: gdb -batch -ex run -ex bt ./prog.
  • O gdb não roda no editor do guia; os depuradores das IDEs fazem o mesmo, com botões.
