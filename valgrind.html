C Valgrind

O Valgrind é um programa que roda o seu programa dentro de uma espécie de máquina virtual e observa cada byte de memória que ele usa: cada malloc, cada free, cada leitura e cada escrita. No fim, ele conta quanta memória ficou sem free (os vazamentos) e, durante a execução, avisa sempre que o programa lê ou escreve onde não devia, ou usa uma variável que nunca recebeu valor. A grande vantagem: não precisa recompilar com nenhuma opção especial. Basta escrever valgrind antes do ./programa.

Você vai aprender
  • A rodar valgrind --leak-check=full ./programa e por que compilar com -g.
  • A ler o HEAP SUMMARY e o LEAK SUMMARY: definitely lost, indirectly lost, still reachable.
  • A ler Invalid write, Invalid read e Invalid free().
  • A achar variáveis sem valor inicial: Conditional jump or move depends on uninitialised value(s) e a opção --track-origins=yes.
  • Quando usar o Valgrind e quando usar os sanitizers, e o que fazer no macOS e no Windows.

Todas as saídas desta aula são reais, feitas com o Valgrind 3.26 e o gcc 15 na máquina fictícia da Ana, na pasta ~/c/vg. O Valgrind não funciona no editor do guia (ele precisa de um programa Linux de verdade); as caixas "Experimente" servem para consertar o que ele encontrou. Para instalar no Ubuntu e no Debian:

$ sudo apt install valgrind

A ideia: o contador de estoque

Na lojinha da Ana, cada produto que sai da prateleira (malloc) tem de voltar ou ser registrado como vendido (free). O Valgrind é o funcionário que fica na porta com uma prancheta: anota tudo o que sai, tudo o que volta, e grita quando alguém mexe numa prateleira vazia ou num produto já devolvido. Quando a loja fecha, ele confere a prancheta e diz: "saíram 3 produtos e voltaram 2; o que faltou saiu pela porta tal, às tantas horas".

Para ele poder dizer "às tantas horas" (o arquivo e a linha), compile com -g, como no gdb.

1. O primeiro relatório: um vazamento

A função copiar reserva memória e devolve o ponteiro. O main usa o texto e esquece do free (veja Vazamentos de Memória):

#include <stdio.h>
#include <stdlib.h>
#include <string.h>

char *copiar(const char *texto) {
    char *copia = malloc(strlen(texto) + 1);
    if (copia != NULL) {
        strcpy(copia, texto);
    }
    return copia;
}

int main(void) {
    char *item = copiar("arroz");
    printf("Item: %s\n", item);
    return 0;
}

4. Variável sem valor inicial: Conditional jump…

Esta é a especialidade do Valgrind, e o que os sanitizers do gcc não pegam. A Ana esqueceu o = 0 da soma:

#include <stdio.h>

int main(void) {
    int notas[] = {7, 8, 10};
    int soma;
    for (int i = 0; i < 3; i++) {
        soma += notas[i];
    }
    if (soma > 20) {
        printf("Passou: %d\n", soma);
    } else {
        printf("Não passou: %d\n", soma);
    }
    return 0;
}

$ gcc -std=c23 -Wall -Wextra -g media.c -o media
$ ./media
Passou: 25

Nem o gcc avisou (o aviso -Wuninitialized do gcc nem sempre aparece sem otimização), e o resultado está certo: a soma começou com 0 por pura sorte, porque aquele pedaço da pilha estava zerado. Em outro programa, ou mais tarde neste mesmo, ela pode começar com qualquer lixo (veja Variáveis). O Valgrind percebe:

Conditional jump or move depends on uninitialised value(s)
"Um desvio condicional (ou uma cópia) depende de valor(es) não inicializado(s)". Em português de gente: um if (ou laço, ou ?:) tomou uma decisão com base num valor que ninguém definiu. É a linha 9: if (soma > 20).
Use of uninitialised value of size 8
"Uso de valor não inicializado": o printf da linha 10 recebeu a soma para escrever na tela. As linhas de cima (_itoa_word, __printf_buffer) são o código interno do printf transformando o número em texto; a linha que interessa é main (media.c:10).
Use --track-origins=yes…
O Valgrind diz onde o valor ruim foi usado, mas não onde ele nasceu. A opção --track-origins=yes ("rastrear origens") responde isso.

Repare que o Valgrind não reclama da linha 7 (soma += notas[i]), onde o lixo entrou na conta: copiar e somar lixo não é proibido. Ele só reclama quando o lixo decide alguma coisa (um if) ou sai do programa (o printf). Por isso, a primeira linha apontada nem sempre é a do erro: siga a pista com o --track-origins=yes.

De onde veio o lixo: --track-origins=yes

$ valgrind --track-origins=yes ./media
«… o cabeçalho …»

==56768==    at 0x40011BC: main (media.c:9)
==56768==  Uninitialised value was created by a stack allocation
==56768==    at 0x4001169: main (media.c:3)
==56768==
«… os outros erros, cada um com a mesma origem …»

"O valor não inicializado foi criado por uma reserva na pilha, em main (media.c:3)": uma variável local do main (as locais moram na pilha; a linha 3 é onde o main começa). Agora é só olhar as variáveis locais do main que nunca recebem valor: a soma. Se o lixo viesse de um malloc, a mensagem seria created by a heap allocation, com a linha do malloc. O --track-origins=yes deixa o Valgrind ainda mais lento, por isso não vem ligado.

5. Os tipos de vazamento

O LEAK SUMMARY tem cinco linhas. Duas aparecem o tempo todo em programas com listas ligadas e structs com ponteiros. Esta lista tem 3 nós, mas o main só libera o primeiro:

#include <stdio.h>
#include <stdlib.h>

struct no {
    int valor;
    struct no *prox;
};

struct no *novo(int valor, struct no *prox) {
    struct no *n = malloc(sizeof *n);
    if (n == NULL) {
        exit(1);
    }
    n->valor = valor;
    n->prox = prox;
    return n;
}

int main(void) {
    struct no *lista = novo(1, novo(2, novo(3, NULL)));
    for (struct no *p = lista; p != NULL; p = p->prox) {
        printf("%d\n", p->valor);
    }
    free(lista);
    return 0;
}

Cada nó tem 16 bytes (um int, 4 bytes de enchimento e um ponteiro de 8; veja sizeof). O nó 1 foi liberado. O nó 2 ficou sem ninguém apontando para ele: definitely lost. O nó 3 ainda tem um ponteiro apontando para ele, mas esse ponteiro mora dentro do nó 2, que está perdido: indirectly lost. Por isso a linha 32 (16 direct, 16 indirect). Conserte o "direto" e o "indireto" some junto.

Linha do LEAK SUMMARYQuer dizerGravidade
definitely lostNenhum ponteiro aponta para o bloco: perdido de vez.Vazamento. Conserte.
indirectly lostSó é apontado por blocos que estão perdidos (o resto de uma lista ou árvore).Some quando você conserta o definitely lost.
possibly lostSó há ponteiros para o meio do bloco, não para o começo.Quase sempre um vazamento; investigue.
still reachableAinda há um ponteiro para o bloco no fim (numa variável global, por exemplo), mas ninguém deu free.Não é perdido, mas é desleixo: libere antes de sair.
suppressedVazamentos que o Valgrind foi mandado ignorar (geralmente de bibliotecas do sistema).Ignore.

Para ver de onde ele veio, o próprio Valgrind ensina: --show-leak-kinds=all ("mostre todos os tipos de vazamento"), que acrescenta 100 bytes in 1 blocks are still reachable in loss record 1 of 1 com by 0x400117A: main (guarda.c:7).

Missão: escreva a função liberar, que libera todos os nós da lista. Cuidado: depois do free(p), não dá mais para ler p->prox (seria um Invalid read). Guarde o próximo numa variável antes do free. Para a missão conferir, mostre liberado N antes de cada free.

#include <stdio.h>
#include <stdlib.h>

struct no {
    int valor;
    struct no *prox;
};

struct no *novo(int valor, struct no *prox) {
    struct no *n = malloc(sizeof *n);
    if (n == NULL) {
        exit(1);
    }
    n->valor = valor;
    n->prox = prox;
    return n;
}

void liberar(struct no *lista) {
    /* libere todos os nós aqui; antes de cada free, mostre "liberado N" */
    printf("liberado %d\n", lista->valor);
    free(lista);
}

int main(void) {
    struct no *lista = novo(1, novo(2, novo(3, NULL)));
    liberar(lista);
    return 0;
}

#include <stdio.h>
#include <stdlib.h>

struct no {
    int valor;
    struct no *prox;
};

struct no *novo(int valor, struct no *prox) {
    struct no *n = malloc(sizeof *n);
    if (n == NULL) {
        exit(1);
    }
    n->valor = valor;
    n->prox = prox;
    return n;
}

void liberar(struct no *lista) {
    struct no *p = lista;
    while (p != NULL) {
        struct no *prox = p->prox;
        printf("liberado %d\n", p->valor);
        free(p);
        p = prox;
    }
}

int main(void) {
    struct no *lista = novo(1, novo(2, novo(3, NULL)));
    liberar(lista);
    return 0;
}

O Memcheck vigia o heap (os blocos do malloc) byte a byte, mas não sabe onde termina cada array local. O estouro de notas[5] da aula Sanitizers, que o ASan chamou de stack-buffer-overflow, passa sem um Invalid read:

Nunca os dois juntos: um programa compilado com -fsanitize=address não roda direito no Valgrind (veja o cenário abaixo).

No macOS e no Windows

O Valgrind oficial não roda nas versões recentes do macOS (nem nos Macs com processador Apple) nem no Windows. Alternativas:

  • Qualquer sistema: os sanitizers (-fsanitize=address) do Clang e do gcc.
  • macOS: o comando leaks (procura vazamentos num programa) e o Instruments, do Xcode.
  • Windows: o Visual Studio tem /fsanitize=address; o Dr. Memory é uma ferramenta gratuita parecida com o Valgrind; e no WSL (o Linux dentro do Windows; veja Instalar no Windows e macOS) o Valgrind funciona normalmente.

Quando dá errado

O relatório mostra main (in /home/ana/c/vg/vaza-semg) em vez de main (vaza.c:14) 
$ gcc -std=c23 -Wall -Wextra vaza.c -o vaza-semg

O que aconteceu: o programa foi compilado sem -g; o Valgrind sabe o nome da função, mas não o arquivo nem a linha ("in executável").

Como resolver: recompile com -g (e, de preferência, sem -O2).

ASan runtime does not come first in initial library list 
$ gcc -std=c23 -Wall -Wextra -g -fsanitize=address notas.c -o notas

O que aconteceu: o programa foi compilado com o AddressSanitizer, e os dois fiscais brigam pela memória. O programa nem rodou (0 allocs), e o 0 errors é enganoso.

Como resolver: para usar o Valgrind, compile sem -fsanitize.

Erros dentro de printf, _itoa_word, strlen…

O que aconteceu: a biblioteca recebeu do seu código um valor sem inicializar ou um ponteiro ruim.

Como resolver: desça a pilha até a primeira linha by …: função (seu-arquivo.c:N). Para valores sem inicializar, rode com --track-origins=yes.

"valgrind: comando não encontrado"

O que aconteceu: o Valgrind não está instalado (ou você está no macOS ou no Windows, onde ele não existe).

Como resolver: no Ubuntu e no Debian, sudo apt install valgrind. Nos outros sistemas, veja as alternativas acima.

O programa pede entrada e o Valgrind "trava"

O que aconteceu: nada travou: o seu programa está esperando você digitar, como sempre. A entrada e os argumentos passam normalmente: valgrind ./prog arg1 < dados.txt.

Como resolver: digite a entrada (ou use < para ler de um arquivo). Lembre que tudo fica mais lento.

Exercícios

1. O comando de sempre

valgrind ./prog

valgrind ./prog

3. Sem linhas

O relatório mostra main (in /home/ana/c/vg/prog), sem número de linha. Qual opção faltou no gcc?

4. O LEAK SUMMARY mostra definitely lost: 16 bytes e indirectly lost: 32 bytes. O que fazer primeiro?

Resumo

  • Compile com -g e rode valgrind --leak-check=full ./programa. Sem recompilar com opções especiais; as linhas com ==PID== são do Valgrind.
  • Invalid read/Invalid write: acesso a memória proibida; as linhas seguintes dizem onde o bloco foi reservado (alloc'd) ou liberado (free'd). Invalid free(): free duplo.
  • Conditional jump or move depends on uninitialised value(s): uma decisão com uma variável sem valor; --track-origins=yes mostra onde ela nasceu.
  • LEAK SUMMARY: conserte os definitely lost (os indirectly lost vão junto); still reachable é memória não liberada mas ainda apontada. A meta é All heap blocks were freed -- no leaks are possible.
  • Valgrind: lento, sem recompilar, pega variáveis sem valor inicial. Sanitizers: rápidos, pegam estouros na pilha e contas inválidas. Nunca os dois juntos.
  • No macOS e no Windows, use os sanitizers, leaks/Instruments, Dr. Memory ou o WSL.
